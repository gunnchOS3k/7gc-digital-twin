# Paper I prospective application-outcome validation — P4 draft v0.1

Question: Do pre-task minimum-useful-service labels predict independently verified application completion under connected, degraded, transitioning and offline conditions? The old classifier and unrelated Bernoulli generator do not answer this.

Primary hypothesis: a capability/resource-aware pre-task classifier reduces the fraction of all exogenously scheduled tasks falsely certified useful relative to the frozen state/support rule. Primary practical-superiority null: mean paired reduction<=0.05; planning alternative 0.10 (gap 0.05); practical target 0.05 absolute reduction, with sensitivity/success-loss guardrail of at most 0.02 (proposed values pending domain review). Labels cannot use post-task outputs. The task oracle is evaluation ground truth, not an eligible predictor.

Primary outcome: per-session false-useful count / all scheduled eligible tasks, baseline minus candidate; denominator fixed before policy decisions. Secondary outcomes: false failures, task correctness, deadline misses, offline completion, stale reads, duplicate/lost mutations, final replica consistency and resource/time traces. If no true failures occur, report the coverage defect rather than certify classifier validity.

Method: scripted synthetic-content workload adapters, isolated processes, independently specified expected outputs/hashes and deadlines; task outcome evaluator blind to classifier labels. Proposed tasks: retrieve a pinned WAIKE lesson and verify bytes; compute a local deterministic exercise against a reference; edit/save/reopen a note with exact content/version; reconcile two synthetic replicas including duplicate and conflicting updates. Include explicitly unsupported server-only tasks and malformed/expired inputs. A connected socket with wrong data,timeout,exhausted CPU/storage or expired content is failure even if state says connected. Separate classification accuracy from controller efficacy.

Inputs: balanced blocked cells for four prospective device-resource profiles×four network states×supported/unsupported tasks, with independently varied CPU/memory/storage pressure and deadlines. Network impairment profiles are proposed delay20/100/600ms,loss0/1/10%,bandwidth0/1/10Mbps plus explicit cut/rejoin events; these are authored stress conditions, not RF measurements. Freshness limits task-specific (e.g. pinned lesson version vs mutable record age); deadlines fixed through task requirements/development calibration, not optimized for a favorable result. Cache prefetch and initial content identical across predictors. Prevent scenario-name lookup and post-outcome leakage. Hold out task instances, impairment schedules and resource combinations, not only RNG integers.

Baselines: frozen state/support classifier, connected-only label, capability-only classifier and proposed resource-aware classifier; all use the same pre-task observations/capability inventory. Diagnostic post-task oracle upper reference is privileged and excluded from the predictor contest. Primary comparator fixed; remaining predictor differences secondary. Execution adapters must attempt all scheduled tasks, regardless of predicted label, to avoid selective verification.

Algorithm specification before outcomes: freeze a deterministic resource/dependency rule from documented required capabilities, maximum content age, predicted task runtime and declared deadline. No learned fit without separately fixed training/tuning procedure. Local compute correctness requires a reference output independent of application code. Semantic acceptability and user benefit remain separate, possibly human-validated extensions.

Units/randomization: independent process/session resets with identical task batches and impairment schedules for paired classifiers; physical device runs,if later authorized,block by device and day. Repeated tasks within one process/device are clustered. Randomize schedule/order within predeclared blocks; no learner records or live accounts. Primary protocol excludes people.

Sample plan: proposed practical delta0.05 and hypothetical pairedSD 0.15;90% power needs about 95sessions,95% half-width0.02 about 217before t-adjustment. Use40 pilot sessions and t-based fixed-n planning with cap 600sessions and budget 8 CPU-hours before heldout. These values are hypothetical design assumptions,not transferred from old synthetic intervals. Distinct from the generic0.02/0.01 example below.

Feasibility/stop rules: startup/input/schema failures stop the harness for repair before heldout; runtime task failures,unsupported operations,deadline/resource violations remain outcomes,not excluded rows. Freeze warmup,warm/cold-cache handling,retry counts and process cleanup. Stop on destructive command,credential/personal-data access or configured compute cap. Do not run impairment/privileged OS operations on the owner's normal networking during preparation.

Reusable code candidates (read-only inspected,not executed as research): Device OS offline_sync.py/vector clocks and service_continuity_execution/sync.py; WAIKE syncCoordinator durable receipt/idempotency behavior and synthetic course fixtures. Some prototype code marks application without modeling transport/deadline enforcement; wrap independent correctness/deadline/freshness checks rather than treating existing tests as application measurements. Exact revisions/paths and limits are in the portal SOFTWARE_REUSE_INVENTORY.md.

Digital-only stage: loopback/mock-transport isolated process tests with declared limits can establish behavior on that host. Physical stage: representative low-resource device,controlled AP/impairment link and independent power-duration/clock observations; no participants required for byte/correctness endpoints. User usefulness,accessibility/learning outcomes or classroom tests require a separate participant protocol. Neither stage has run here.

## Statistical and reproducibility rules
Use one primary paired contrast, a fixed exogenous workload/scenario mixture and whole-seed/session means. Each policy/model receives the same exogenous inputs in its paired unit; policy-dependent queues/batteries evolve separately. Never pool this study with historical generators. Correctness checks and pilot/training samples are excluded from confirmatory inference. Primary two-sided95% paired Student-t interval, sample SD(ddof1) and paired differences; disclose distribution/dependence assumptions and influential pairs. Secondary bootstrap sensitivity is descriptive at the independent unit; do not resample slots/tasks as independent when clustered. Zero-crossing is inconclusive, not equivalence. Secondary confirmatory families use Holm; remaining subgroups are explicitly exploratory. Report all planned outcomes, harms, missing/invalid actions, timeouts and precision failures.

Planning example uses a hypothetical paired SD 0.15, not measured/calculated from old means. For practical delta 0.02,power 0.90 and two-sided alpha 0.05, normal planning gives approximately592paired units; half-width 0.01 needs865. Use iterative t-quantile planning in Paper II tooling; a40-unit prospective development pilot would estimate SD and select n before any heldout outcome is read, minimum 30, maximum 2500. Starting expectation is about 900units if the hypothetical variance holds, not a fixed guarantee of power. If required n exceeds cap or resource estimate, stop before heldout and revise/seek approval. Pilot variance selection has uncertainty; archive that estimate and sensitivity. These are proposed future counts; no seeds are expanded now. Do not append units after viewing heldout results.

Derive disjoint pilot/training/heldout seed streams from approved study/config SHA and split/index using SHA256; archive actual seed lists and input hashes only in the separately authorized milestone. No reserved future seed list or outcome is created here. Freeze policies, tuning bounds, scenario mixture, n and stopping/multiplicity rules before heldout. An independent reviewer should audit the freeze and holdout access log. Archive source/config SHAs, dependencies, hardware/runtime, observations/actions/rejections/compute/cost traces, raw task outcomes, seed-level summaries, independent analysis, data dictionary and SHA256SUMS. A checksum establishes bytes, not validity or ownership.

Human decisions: approve science/effect size/sampling and device/workload assumptions; settle rights/permissions, intended claims, required coauthors/contributions/funding/conflicts and patent/IP concerns; authorize a separate execution milestone. Human scientific approval and external publication authorization remain false. Synthetic process experiments do not establish a human-participant ethics exemption; studies with people need an appropriate separate review.

## Practical-effect and guardrail clarification
Prospective primary success requires the lower 95% paired interval for false-useful reduction to exceed 0.05,and the upper 95% paired interval for false-failure increase to remain at most 0.02. Power planning uses hypothetical alternative 0.10against margin 0.05 (gap 0.05); it does not promise power at the null boundary. Both conditions must pass; otherwise report harmful,inconclusive or insufficient practical benefit as applicable. These are proposed rules requiring domain review,not observed effects.

P4 statistical-design clarification: the generic sample-size illustration below uses an effect GAP of 0.02; when testing practical superiority over0.02,the planning alternative is0.04. It must not be read as 90% power to demonstrate an effect greater than0.02when the true effect equals0.02. Actual effect/margin choices require human/domain justification before freezing.
